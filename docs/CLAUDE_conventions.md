# 프론트엔드 개발 규칙 (ohgiraffer_fe)

## 1. 에러 메시지 처리 원칙

- 화면에 노출하는 에러 메시지는 **백엔드가 내려주는 에러코드 + 메시지**를 그대로 사용한다.
- 프론트에서 임의로 에러 문구를 재해석하거나 하드코딩하지 않는다. 단, 다음 경우는 예외로 프론트가 자체 메시지를 구성한다:
   - 네트워크 자체 실패(백엔드 응답을 아예 못 받은 경우)
   - 입력값 검증 실패 등 프론트 단계에서 먼저 걸러지는 경우
- 에러코드별 분기 처리가 필요한 경우, 에러코드를 문자열로 하드코딩해 여기저기 흩어놓지 말고 한곳에 상수/매핑으로 관리한다.

## 2. `src/app/` 폴더 규칙

- `src/app/` 하위의 모든 폴더는 **`page.tsx`와 `layout.tsx`만 가질 수 있다.**
- `components/`, `_components/` 등 UI 조각 폴더를 `app/` 안에 별도로 두지 않는다.
- `page.tsx`는 `src/features/` 안의 컴포넌트를 조립하는 역할만 한다 (자체적으로 마크업/로직을 길게 작성하지 않는다).
- 클라이언트 상태·상호작용이 필요해 여러 컴포넌트를 미리 조합해야 하는 경우, `src/features/{도메인}/components/` 안에 `~~~Client.tsx` 파일을 만들어 조합한 뒤 `page.tsx`에서 import한다.
   - 예: `page.tsx` → `<SomeFeaturePageClient {...props} />`

## 3. 폴더 구조

ohgiraffer_fe/
├── public/ # 프로젝트에서 쓰이는 모든 이미지 파일 (전부 여기 한 곳에 모음)
├── src/
│ ├── app/ # 라우팅 전용 - 각 폴더에 page.tsx / layout.tsx 만 존재
│ ├── components/ # 전역 공통 요소만
│ │ ├── layout/ # 헤더/사이드바/푸터 등 공통 레이아웃
│ │ ├── modals/ # 전역에서 재사용하는 공통 모달
│ │ └── ui/ # shadcn으로 받은 UI 컴포넌트
│ ├── features/ # 도메인/페이지별 기능 단위
│ │ └── {도메인}/
│ │ ├── components/ # 이 도메인 전용 컴포넌트 (~~~Client.tsx 포함)
│ │ ├── hooks/ # 이 페이지/기능에서만 쓰는 훅
│ │ ├── actions.ts # 서버 액션
│ │ └── types.ts # 이 도메인의 타입 정의
│ ├── lib/ # 프레임워크 독립적인 순수 유틸 함수
│ └── services/ # 백엔드 API 호출 전담 (fetch 래퍼, UI 로직 없음)

**규칙**: `features/` 하위 각 도메인 폴더는 반드시 `components/`, `actions.ts`, `types.ts`를 갖추고, 그 도메인 페이지에서만 쓰는 훅은 반드시 `hooks/` 폴더 안에 넣는다(다른 도메인에서도 재사용되는 훅이라면 공용 위치로 승격을 검토한다).

## 4. 컴포넌트 분리 원칙

- 모든 페이지/기능 작업은 **컴포넌트 분리를 기본 전제로** 진행한다. 하나의 큰 컴포넌트에 로직과 마크업을 몰아넣지 않는다.
- **(AI 어시스턴트 작업 시 필수 절차)** 컴포넌트 분리 작업을 실제로 진행하기 전에, Claude Code는 반드시 예상되는 파일 구조도(어떤 파일이 새로 생기고 무엇을 담을지)를 먼저 제시하고, 사용자 확인을 받은 뒤에 진행한다. 확인 없이 임의로 파일을 나누지 않는다.

## 5. 중복 요청 방지 원칙

결제/삭제 등 부작용이 있는 액션은 버튼 `disabled` 상태만으로 막지 말고, `useRef` 기반의 동기 가드(예: `isSubmittingRef`)를 함께 둔다. React state 업데이트는 비동기라 `disabled` 하나만으로는 빠른 연타(더블클릭)를 완전히 막지 못한다.

## 6. 세션 만료 공통 처리

인증이 필요한 서버 컴포넌트는 API 호출을 반드시 try/catch로 감싸고, 인증 세션 오류는 전용 리다이렉트 컴포넌트로 처리한다. 그냥 두면 예외가 그대로 전파되어 Next.js 기본 에러 화면으로 전체 페이지가 깨진다.

## 7. Fail-safe 기본값 원칙

점검 모드·권한 확인처럼 보안/가용성에 관련된 조회가 실패했을 때, "문제없음"으로 기본 처리하지 않고 안전한 쪽(예: 점검 중으로 간주, 권한 없음으로 간주)으로 기본값을 둔다.

## 8. 무거운 라이브러리 도입 전 검토

차트·애니메이션 등 특정 UI 하나를 위해 큰 라이브러리를 새로 추가하기 전에, 순수 CSS/SVG로 충분히 구현 가능한지 먼저 검토한다.

## 9. 중복 구현 전 공용 컴포넌트 확인

검색창, 페이지네이션, 모달처럼 여러 화면에서 비슷하게 필요한 UI는 새로 만들기 전에 `src/components/`에 이미 있는지 먼저 확인한다.

## 10. 타입/에러 구분

API 응답 처리 시 "서버 오류"와 "입력값 검증 오류"를 구분해서 사용자에게 다른 안내를 준다(둘 다 같은 문구로 뭉뚱그리지 않는다).

## 11. 네이밍 컨벤션

컴포넌트는 PascalCase, 훅은 `use` 접두사 + camelCase, 서버 액션 파일은 `actions.ts`로 통일한다.

## 12. 주석 규칙

주석은 한국어로, 코드가 이미 보여주는 "무엇을"이 아니라 "왜 이렇게 했는지"만 남긴다.

## 13. PR 전 체크리스트

`tsc --noEmit`, `eslint` 통과를 확인한 후 PR을 생성한다. 특히 기존에 있던 lint 경고와 이번 변경으로 새로 생긴 경고를 구분해서 확인한다(예: 수정 전/후를 비교해 새로 발생한 문제인지 확인).

## 14. `robots.ts` 관리

이번 프로젝트는 검색엔진에 노출할 공개 페이지가 없으므로, src/app/robots.ts에서 전체 경로 크롤링을 차단한다.

export default function robots(): MetadataRoute.Robots {
return {
rules: {
userAgent: '*',
disallow: '/',
},
};
}
향후 검색엔진에 노출하고 싶은 공개 페이지가 생기면, 그 시점에 sitemap.ts 도입 여부와 robots.ts의 disallow 범위를 다시 검토한다.

## 15. `proxy.ts` (미들웨어) 작업 규칙

`proxy.ts`는 다음 두 가지 접근 제한에 사용한다:

- 비로그인 사용자의 보호된 경로 접근 차단(로그인 페이지로 리다이렉트)
- 로그인은 했지만 필요한 권한이 없는 사용자의 접근 차단(role 값이 요구 조건과 다른 경우, 예: 학생이 `/admin` 접근)

이 파일은 **모든 요청에 영향을 주는 보안 관련 파일**이라, 수정이 필요한 경우 작업을 시작하기 전에 반드시 개발자에게 변경 내용을 먼저 설명하고 확인을 받은 뒤 진행한다. 확인 없이 임의로 경로 목록이나 조건을 바꾸지 않는다.
